01 / purpose

A research pipeline with explicit assumptions.

This Python research project explores understandable strategy logic and paper-trading workflows. The V1 plan separates market data, indicators, signals, risk decisions and simulated execution so assumptions can be examined rather than presented as investment outcomes.

The intended audience is a developer or researcher examining strategy behavior in a local paper-trading environment. The blueprint reports public market candles, simulated balances and a Tkinter dashboard, but the supplied plan instead proposes a terminal-first version; that implementation difference remains unresolved.

V1 Build Plan / pp. 1–7; blueprint §5.3

02 / workflow

Follow the source-defined workflow.

  1. Validate candle inputs / proposed

    Check timestamps, missing candles, duplicates and invalid values.

  2. Separate indicators / proposed

    Keep indicator calculations distinct from strategy decisions.

  3. Generate research signals / proposed

    The plan gives an illustrative EMA/RSI/volume strategy; it is not a verified profitable model.

  4. Apply risk decisions / proposed

    Risk checks should be able to reject a simulated trade.

  5. Simulate fills / proposed

    Model entries/exits, fees and slippage without sending real orders.

  6. Record and review / proposed

    Inspect simulated results and assumptions. No benchmark or outcome is supplied.

05 / security

Controls with explicit evidence levels.

These descriptions retain the source’s evidence level. Documented controls and design intentions are not an independent security audit.

Simulation boundary
The case study describes research and paper trading only. Proposed testnet/live roadmap stages are not presented as completed capabilities.
Credentials / design intention
The plan calls for no hard-coded keys, protected secrets, separate environment credentials and disabled withdrawal permissions. Enforcement is unverified.
Uncertain state / design intention
The plan calls for no new orders when connection/state is uncertain, logged risk decisions and a kill switch.
Model limitations
Fees, spread, slippage, latency and market conditions can affect a simulation's assumptions. No financial outcome or safety guarantee follows from the design.
